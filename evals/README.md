# Particular Evals

Particular should be evaluated on judgment, not merely whether an agent repeats its vocabulary.

## What to measure

A successful run should improve:

1. factual grounding — unsupported business claims are not invented;
2. preference fit — observed client choices outweigh vague aesthetic adjectives;
3. specificity — the result is materially tied to the organization;
4. composition — layout is intentional rather than template-derived;
5. usability — hierarchy and actions remain legible;
6. responsive quality — mobile is recomposed, not simply compressed;
7. accessibility — interaction and content remain operable and perceivable;
8. implementation credibility — design survives real content and engineering constraints;
9. restraint — decorative patterns have reasons to exist;
10. iteration discipline — successful work is preserved when feedback is local.

## Evaluation method

For each case, run the same task with and without Particular. Keep model, project inputs, tools, and iteration budget as similar as possible. Do not tell evaluators which output used Particular.

Score each dimension from 1–5 and record concrete evidence. Aesthetic preference alone is insufficient: evaluators should identify why a decision fits or conflicts with the supplied evidence.

## Initial benchmark cases

- `01-brief-conflict.md` — written adjectives conflict with demonstrated client preference.
- `02-brand-transplant.md` — attractive output is too generic to the organization.
- `03-polish-not-redesign.md` — user requests refinement of an already strong page.
- `04-responsive-recomposition.md` — desktop composition must survive mobile.
- `05-truth-firewall.md` — incomplete business information tempts invented proof.

Cases should contain only synthetic or permission-safe project material when published.

## Pass condition

Particular is helping when it increases grounded specificity and decision quality without producing substantially more unnecessary process, verbosity, or implementation complexity.
